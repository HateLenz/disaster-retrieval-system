# 灾后检索系统需求分析

## 1. 项目背景

灾害发生后，快速获取灾前遥感影像能够辅助灾情研判、建筑物损毁比对和应急资源调度。传统方式通常依赖人工在历史影像库中查找同一地点或相似场景，效率较低，且不利于在无网络环境下部署。

本系统面向 xBD 数据集中的建筑级灾前/灾后影像检索任务，以本地部署的 `clip_visual_baseline_smoke_stage1_v2.pt` 模型为核心，构建一个支持离线运行的灾后检索桌面系统。用户输入 hold 集中的任意灾后图像，并选择灾害类型 `disaster_type` 和灾害地区 `disaster`，系统在后端 hold 灾前数据库中检索并返回 Top 5 灾前图像。

## 2. 建设目标

系统建设目标分为算法目标和应用目标两部分：

- 算法目标：完成灾后图像到灾前图像的特征编码、向量检索和 Top-K 排序输出。
- 应用目标：提供可交互、可演示、可离线运行、可维护的桌面应用，覆盖数据选择、检索、结果查看、状态诊断和结果导出等完整流程。

当前系统不应只停留在“上传图片并返回结果”的简单形态。作为毕业设计系统，应用层应体现完整的信息系统能力，包括检索条件管理、结果可视化、历史记录、索引管理、系统状态监控、测试评估和离线部署能力。

## 3. 用户角色

| 角色 | 主要诉求 | 典型操作 |
| --- | --- | --- |
| 检索用户 `retriever` | 快速找到灾后图像对应或相似的灾前图像 | 上传图像、选择灾害类型和地区、查看 Top 5、反馈、导出报告和本人历史数据 |
| 系统管理员 `admin` | 维护账号、权限、索引和本地资源 | 查看系统状态、重载/重建索引、维护检索用户、导出失败案例 CSV |
| 算法开发人员 `developer` | 分析模型效果和失败案例 | 查看全部用户、查看失败案例、导出失败案例 CSV、切换模型、算法分析和检索策略统计 |

系统服务于灾情研判场景，但权限模型不再单独设置“研判人员”角色。灾情研判业务中的检索、对比、反馈和报告导出由检索用户完成；模型效果分析由算法开发人员完成；系统运行维护由系统管理员完成。

## 4. 业务流程

### 4.1 离线建库流程

1. 读取 xBD hold split 的建筑级 patch 元信息。
2. 加载本地 CLIP 视觉检索模型。
3. 对灾前图像或灾前 patch 提取特征。
4. 保存特征矩阵、FAISS 索引和 SQLite 元信息。
5. 后端启动时加载索引和模型，进入本地可检索状态。

### 4.2 在线检索流程

1. 用户在前端选择 `disaster_type` 和 `disaster`。
2. 用户上传灾后图像，或从 hold 样例中选择灾后图像。
3. 前端通过 HTTP 请求调用 FastAPI 后端。
4. 后端对灾后图像编码，按灾害类型和地区过滤灾前候选库。
5. FAISS 执行向量相似性搜索。
6. 后端聚合 patch 级匹配分数，返回 Top 5 灾前图像及元信息。
7. 前端展示结果缩略图、分数、灾害信息、建筑 ID 和图像路径。

## 6. 非功能需求

| 类别 | 需求 |
| --- | --- |
| 离线性 | 模型、索引、元信息和前端资源均部署在本地，不依赖外部网络 |
| 响应时间 | 单张 224x224 patch 查询应在秒级返回；完整图像滑窗查询应控制在可交互范围内 |
| 可用性 | 前端应提供清晰的状态提示、错误提示和样例入口 |
| 可维护性 | 算法、API、前端和索引构建脚本分层清晰 |
| 可扩展性 | 后续可替换模型、扩展 Stage-2 文本语义增强或接入更多数据 split |
| 可测试性 | 后端 API、索引构建、检索结果、前端交互均应有明确测试方案 |
| 安全性 | 只允许读取仓库内数据资源，避免任意文件访问 |
| 鲁棒性 | 模型或索引缺失时应返回可理解的错误信息 |

## 7. 数据需求

系统使用的数据主要包括：

- xBD building patch 元信息：`data/processed/xbd_building_patches.csv`
- hold 灾前 patch 图像：`pre_patch_path`
- hold 灾后 patch 图像：`post_patch_path`
- 灾害类型：`disaster_type`
- 灾害地区或灾害事件：`disaster`
- 建筑标识：`building_id`、`building_uid`、`positive_id`
- 检索索引：`indexes/api_hold_stage1_v2/pre_features.npy`
- SQLite 元信息库：`db/retrieval_hold_stage1_v2.db`

## 8. 约束条件

- 当前最佳模型假设为 `clip_visual_baseline_smoke_stage1_v2.pt`。
- 检索库限定为 xBD hold split 的灾前数据。
- 用户查询图像主要来自 xBD hold split 的灾后图像。
- 系统以本地桌面应用为目标，不依赖云端推理服务。
- 当前应用部署以视觉特征检索为主，代码中保留文本语义增强实验链路和本地 checkpoint 切换能力。

## 9. 验收标准

系统达到以下条件可认为应用开发部分满足毕设系统要求：

1. 能在本地启动后端和前端。
2. 能加载本地模型和本地索引。
3. 能选择灾害类型和灾害地区。
4. 能上传或选择灾后图像并返回 Top 5 灾前结果。
5. 能查看系统状态、索引规模和模型路径。
6. 能保存或导出一次检索的结果信息。
7. 能通过测试文档中的功能测试、接口测试和异常测试。
