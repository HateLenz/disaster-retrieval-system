# 业务分析

## 1. 业务需求

灾害发生后，灾情研判业务通常需要将灾后遥感影像与灾前影像进行对比，以辅助判断建筑损毁情况、灾害影响范围和应急处置优先级。传统处理方式依赖人工在历史影像库中查找对应或相似的灾前图像，效率较低，且在灾后通信条件不稳定的场景下难以依赖在线平台完成检索。

本系统面向 xBD 数据集中的灾前/灾后建筑级遥感影像，构建一个支持本地离线运行的灾后检索系统。系统以已部署在本地的 CLIP 视觉检索模型为核心，将 hold 数据集中的灾前数据作为后端灾前数据库。用户输入 hold 中任意灾后图像，并选择灾害类型 `disaster_type` 和灾害地区 `disaster` 后，系统在灾前数据库中检索出 Top 5 灾前图像，并展示相似度分数和相关元信息。

从业务角度看，系统需要满足以下需求：

| 编号 | 业务需求 | 说明 |
| --- | --- | --- |
| BR-01 | 灾后图像检索 | 用户能够上传或选择灾后图像，并获得 Top 5 灾前检索结果 |
| BR-02 | 灾害条件筛选 | 用户能够按照灾害类型和灾害地区缩小候选范围，提高检索针对性 |
| BR-03 | 灾前灾后对比 | 用户能够查看查询灾后图像和命中灾前图像，辅助人工判断 |
| BR-04 | 检索过程留痕 | 系统能够保存检索历史，便于复现、追踪和后续分析 |
| BR-05 | 结果报告导出 | 用户能够将一次检索结果导出为报告，用于记录和答辩展示 |
| BR-06 | 多角色使用 | 系统区分检索用户、系统管理员和算法开发人员三类角色 |
| BR-07 | 离线部署运行 | 模型、索引、元信息和账号数据均保存在本地，不依赖云端服务 |
| BR-08 | 系统维护管理 | 管理员能够查看模型、索引、设备和本地数据库状态 |

系统服务于灾情研判业务场景，但不把“研判人员”设置为独立系统角色。权限模型中只保留三类角色：检索用户面向业务使用，负责完成灾后图像检索、结果查看、反馈标注和报告导出；系统管理员面向运行维护，负责账号权限、系统状态、索引任务和本地资源管理；算法开发人员面向模型优化，负责失败案例分析、模型效果评估和检索策略调试。

系统的核心业务闭环为：

```text
用户登录 -> 选择灾害条件 -> 输入灾后图像 -> 执行检索 -> 查看 Top 5 灾前结果
-> 查看详情与前后对比 -> 标记反馈 -> 保存历史 -> 导出报告
```

## 2. 用例详述

### 2.1 用例一：用户登录与角色识别

| 项目 | 内容 |
| --- | --- |
| 用例名称 | 用户登录与角色识别 |
| 参与者 | 检索用户、系统管理员、算法开发人员 |
| 触发条件 | 用户打开系统，需要进入对应角色的工作界面 |
| 前置条件 | 系统已启动，SQLite 用户表已初始化 |
| 后置条件 | 用户成功登录，系统根据角色展示对应功能 |

基本流程：

1. 用户打开灾后检索系统。
2. 系统显示登录/注册界面。
3. 用户输入用户名和密码。
4. 后端校验账号密码，并生成本地会话 token。
5. 前端保存会话 token。
6. 系统根据用户角色展示不同功能入口。

扩展流程：

- 如果用户尚无账号，可在注册界面创建本地检索用户账号，后续由管理员调整角色。
- 如果账号或密码错误，系统提示登录失败。
- 如果会话过期，系统要求用户重新登录。

异常处理：

| 异常 | 处理方式 |
| --- | --- |
| 用户名不存在 | 返回登录失败提示 |
| 密码错误 | 返回登录失败提示 |
| token 失效 | 返回 401，前端清除登录状态 |
| 检索用户访问管理接口 | 返回 403，无权限访问 |

### 2.2 用例二：单张灾后图像检索

| 项目 | 内容 |
| --- | --- |
| 用例名称 | 单张灾后图像检索 |
| 参与者 | 检索用户 |
| 触发条件 | 用户需要根据一张灾后图像查找对应或相似的灾前图像 |
| 前置条件 | 用户已登录，后端模型和索引已加载 |
| 后置条件 | 系统返回 Top 5 灾前图像并保存检索记录 |

基本流程：

1. 用户进入检索工作台。
2. 用户选择灾害类型 `disaster_type`。
3. 用户选择灾害地区 `disaster`。
4. 用户上传一张灾后图像，或选择系统提供的 hold 样例。
5. 用户点击“检索 Top 5”。
6. 前端将图像和筛选条件发送给后端。
7. 后端对灾后图像进行预处理和特征编码。
8. 后端根据灾害类型和地区过滤灾前候选库。
9. 后端调用 FAISS 进行相似性检索。
10. 系统返回 Top 5 灾前图像、相似度分数和元信息。
11. 前端展示检索结果，并将本次检索写入历史记录。

扩展流程：

- 用户可以切换候选过滤模式，如只按灾害类型过滤、只按灾害地区过滤或全库检索。
- 用户可以切换排序策略，如 Top-M 均值、最高分、均值、求和和投票数。
- 用户可以点击结果卡片查看灾前灾后对比详情。

异常处理：

| 异常 | 处理方式 |
| --- | --- |
| 未选择图像 | 前端提示请选择查询图像 |
| 图像格式错误 | 后端返回图像读取错误 |
| 候选库为空 | 后端返回无匹配候选提示 |
| 模型或索引未加载 | 后端返回服务未就绪提示 |

### 2.3 用例三：检索结果分析、反馈与报告导出

| 项目 | 内容 |
| --- | --- |
| 用例名称 | 检索结果分析、反馈与报告导出 |
| 参与者 | 检索用户、算法开发人员 |
| 触发条件 | 用户需要对检索结果进行人工判断、保存和复盘 |
| 前置条件 | 已完成一次检索，系统存在检索结果 |
| 后置条件 | 结果反馈被保存，报告文件可导出 |

基本流程：

1. 用户在检索结果列表中点击某个结果。
2. 系统展示查询灾后图像和命中灾前图像。
3. 用户查看相似度分数、tile ID、building UID、灾害类型、损毁标签等元信息。
4. 用户根据人工判断标记结果为“正确”“错误”或“不确定”。
5. 系统将反馈写入本地数据库。
6. 用户进入历史记录页面，选择某一次检索。
7. 用户点击导出报告。
8. 系统生成 Markdown 检索报告。

扩展流程：

- 如果结果被标记为“错误”，系统将其纳入失败案例库。
- 检索用户可以完成结果反馈和报告导出。
- 算法开发人员可根据失败案例分析模型局限性。

异常处理：

| 异常 | 处理方式 |
| --- | --- |
| 历史记录不存在 | 返回记录不存在提示 |
| 用户无权查看他人记录 | 返回权限不足提示 |
| 报告生成失败 | 返回导出失败提示 |
| 反馈内容非法 | 返回反馈类型错误提示 |

### 2.4 用例四：检索历史与失败案例管理

| 项目 | 内容 |
| --- | --- |
| 用例名称 | 检索历史与失败案例管理 |
| 参与者 | 检索用户、系统管理员、算法开发人员 |
| 触发条件 | 用户需要查看以往检索记录，或分析检索效果较差的案例 |
| 前置条件 | 用户已登录，系统中已经存在至少一次检索记录 |
| 后置条件 | 用户能够查看历史详情，管理员和算法开发人员能够查看失败案例 |

基本流程：

1. 用户进入检索历史页面。
2. 系统根据用户角色加载历史记录。
3. 检索用户只能查看本人历史，管理员和算法开发人员可以查看全部历史。
4. 用户点击某条历史记录。
5. 系统展示该次检索的查询条件、候选库信息、Top 5 结果和检索耗时。
6. 用户可以重新查看结果详情，或导出检索报告。
7. 管理员或算法开发人员进入失败案例库。
8. 系统展示低分检索记录和被标记为错误的结果。

扩展流程：

- 用户可以通过历史记录复现一次检索结果。
- 算法开发人员可以根据失败案例分析模型局限性。
- 管理员可以结合历史记录观察系统使用情况。

异常处理：

| 异常 | 处理方式 |
| --- | --- |
| 历史记录不存在 | 返回记录不存在提示 |
| 检索用户访问他人历史 | 返回权限不足提示 |
| 当前无失败案例 | 显示空状态 |
| 报告导出失败 | 返回导出失败提示 |

### 2.5 用例五：系统状态、索引与用户管理

| 项目 | 内容 |
| --- | --- |
| 用例名称 | 系统状态、索引与用户管理 |
| 参与者 | 系统管理员、算法开发人员 |
| 触发条件 | 用户需要确认模型、索引和设备状态，或维护灾前数据库与本地账号 |
| 前置条件 | 管理员或开发人员已登录 |
| 后置条件 | 用户能够查看系统状态，完成索引维护、用户查看或检索用户维护，算法开发人员能够完成模型切换与算法分析 |

基本流程：

1. 管理员或算法开发人员进入系统状态页面。
2. 系统展示当前模型 checkpoint 路径、索引范围、图库 patch 数、tile 数、推理设备和 CUDA 状态。
3. 系统展示特征文件、元信息文件、SQLite 数据库等本地资源是否存在。
4. 管理员或算法开发人员可点击“重载索引”，使服务重新加载本地模型和索引。
5. 管理员或算法开发人员可点击“重建完整 hold 索引”，后台执行索引构建脚本。
6. 系统展示索引任务状态、进程号、日志路径和操作反馈。
7. 管理员进入用户管理页面，查询、新增、修改或停用检索用户。
8. 算法开发人员进入用户管理页面，查看全部用户信息。
9. 算法开发人员进入算法分析页面，查看检索统计、失败案例统计、策略统计和本地 checkpoint 列表，并可切换当前检索模型。

扩展流程：

- 如果索引重建任务正在运行，系统展示运行状态、进程号和日志路径。
- 如果算法开发人员切换模型，系统重新加载模型与索引，并展示当前服务是否就绪。

异常处理：

| 异常 | 处理方式 |
| --- | --- |
| 检索用户访问索引管理 | 返回权限不足 |
| 索引构建任务已在运行 | 返回任务冲突提示 |
| checkpoint 缺失 | 系统状态显示模型文件缺失 |
| 特征文件缺失 | 系统提示需重新构建索引 |
| 管理员修改 developer 账号 | 返回权限不足 |
| 非 developer 访问算法分析或模型切换 | 返回权限不足 |

## 3. 非功能性需求

### 3.1 离线性

系统必须支持本地离线运行。模型权重、检索索引、SQLite 数据库、前端资源和 xBD 图像文件均保存在本地。系统运行过程中不依赖在线推理服务和远程数据库。

### 3.2 响应性能

系统应满足交互式检索需求。对于建筑级 patch 图像，检索结果应在较短时间内返回；对于较大遥感图像，系统可通过滑窗切分完成检索，并在界面中展示检索耗时。

### 3.3 可用性

前端界面应清晰展示检索状态、模型状态、候选库规模和错误提示。用户不需要理解底层模型细节即可完成图像输入、条件选择和结果查看。

### 3.4 安全性

系统应具备基础访问控制。未登录用户不能调用检索和管理接口；检索用户不能访问用户管理和索引管理功能；管理员不能查看 developer 用户信息；开发人员可以查看全部用户信息但不负责账号修改。图像资源接口只允许访问仓库目录内的文件，避免任意文件读取。

### 3.5 可维护性

系统应采用分层结构。前端负责交互展示，FastAPI 负责接口服务，检索服务负责模型和索引调用，SQLite 负责本地业务数据存储。各模块职责清晰，便于维护。

### 3.6 可扩展性

系统应具备可配置能力，包括替换模型 checkpoint、切换完整 hold 索引、使用文本语义增强实验模型、配置检索策略、导出报告和接入不同数据集 split。

### 3.7 可靠性

当模型、索引或数据文件缺失时，系统应返回明确错误信息，而不是直接崩溃。检索历史、用户反馈和账号信息应持久化保存到 SQLite 中。

### 3.8 可测试性

系统应提供清晰的接口和测试路径。后端接口可通过 FastAPI TestClient 或 HTTP 请求测试；前端功能可通过实际界面操作验证；检索结果、历史记录、报告导出和权限控制均应有对应测试用例。

## 4. 本章小结

本章从业务角度分析了灾后检索系统的建设需求。系统的核心业务目标是在本地离线环境下，根据用户输入的灾后遥感图像和灾害条件，从 hold 灾前数据库中检索出 Top 5 灾前图像，并辅助用户完成结果查看、对比分析、反馈标注和报告导出。

围绕该目标，本章定义了系统的主要业务需求，并对用户登录与角色识别、单张灾后图像检索、检索结果分析与报告导出、检索历史与失败案例管理、系统状态查看与索引管理五个典型用例进行了详细说明。同时，本章从离线性、响应性能、可用性、安全性、可维护性、可扩展性、可靠性和可测试性等方面提出了非功能性需求。

通过上述业务分析，可以明确本系统不仅是一个算法检索脚本，而是一个具备多角色使用、检索业务闭环、结果留痕和本地维护能力的灾后遥感图像检索应用系统。
